# Custom Nufon App Launch

## Status

Design proposal.

## Purpose

Nufon should be able to launch user-installed custom apps from a chat or peer
context. Custom apps may be generated by coding agents and can implement their
own UI and interaction model while using Nufon-managed identity and connection
access.

```text
Nufon GUI
  → selected peer/conversation
  → registered custom app
  → scoped launch session
  → custom app uses Nufon CLI/service
```

Nufon owns identity, trust, and access. The custom app owns its UI and
application logic.

## App registration

Nufon discovers custom apps through an explicit registration manifest. The
first implementation should use explicit registration rather than automatic
application discovery.

Example:

```json
{
  "id": "com.example.voice-inbox",
  "name": "Voice Inbox",
  "version": "1.0.0",
  "executable": "/Applications/VoiceInbox.app",
  "handles": ["voice_message", "live_audio"],
  "requested_capabilities": [
    "message.receive",
    "recording.fetch"
  ]
}
```

The manifest should be associated with the installed application where
possible. Nufon should verify that the executable path and application
identity match the registered entry before launching it.

### Registry operations

The GUI needs only a small registry:

```text
register app
unregister app
list apps
set default app for interaction type
```

A custom app may be selected manually from the chat window:

```text
Open with…
  Default Chat
  Voice Inbox
  Other registered app
```

Automatic selection can be added later using the manifest's `handles` field.

## Selection rules

Nufon chooses an app in this order:

1. Explicit app selected by the user.
2. App configured as the default for the interaction type.
3. An installed app whose manifest handles the interaction type.
4. Nufon's built-in chat view.

Nufon must not launch an app solely because it requests a capability. The app
must be registered and the user must approve its requested access.

## Launch handoff

Nufon should launch the custom app with a short-lived session token:

```sh
VoiceInbox --nufon-session <opaque-token>
```

The token is an opaque reference. It must not contain private keys or depend
on command-line-visible identity secrets.

The custom app exchanges the token with the local Nufon service or CLI and
receives its approved context:

```json
{
  "identity": "default",
  "peer": "bob",
  "conversation": "conversation-123",
  "capabilities": [
    "message.send",
    "message.receive"
  ],
  "expires_at": "2026-12-31T18:00:00Z"
}
```

The session should be:

- scoped to one app;
- scoped to one identity and conversation where possible;
- limited to approved capabilities;
- short-lived or revocable;
- invalid after logout or identity revocation;
- unusable by another registered application.

## Context sources

The launch context may include:

```text
selected identity
peer identity and display name
conversation ID
interaction type
selected message or recording ID
approved capabilities
session expiration
```

It should not include:

```text
private identity keys
unrestricted endpoint credentials
unredacted policy databases
other peers' private data
```

## App-to-Nufon communication

The initial integration can use the standalone CLI:

```sh
nufon session info <token>
nufon session send <token> --method message.send --json '{"text":"hello"}'
nufon session events <token> --follow
```

The CLI remains responsible for agent-to-agent operations. The custom app
uses the session token rather than directly managing Nufon identity keys.

A later implementation may replace subprocess calls with local IPC while
preserving the same logical session API.

## Launch flow

```text
1. User selects a peer or opens a chat.
2. User chooses Open with… or Nufon selects a configured default.
3. Nufon reads the app manifest.
4. Nufon checks requested capabilities and existing approval.
5. Nufon asks for approval if needed.
6. Nufon creates a scoped session.
7. Nufon launches the executable with the session token.
8. Custom app calls Nufon CLI/service with the token.
9. Nufon validates the token and returns approved context.
10. Custom app performs permitted operations.
```

## App manifest capabilities

The manifest declares requested capabilities, but does not grant them.

```json
{
  "requested_capabilities": [
    "message.receive",
    "message.send",
    "recording.fetch"
  ]
}
```

Nufon should show the request in user-facing terms:

```text
Voice Inbox wants to:
- receive messages from Bob
- send messages to Bob
- fetch shared recordings
```

The user may approve a subset. The generated session contains only the
approved subset.

Capability names should use logical operations rather than implementation
commands. For example, use `message.send`, not `iroh.sender.send`.

## Security requirements

- Treat application registration as a trust decision.
- Never pass private keys through argv, environment variables, or context files.
- Do not make session tokens reusable indefinitely.
- Bind sessions to the registered application identity where possible.
- Validate peer, identity, conversation, and capability on every operation.
- Expire and revoke sessions locally without peer cooperation.
- Log app launches, approvals, denials, and sensitive operations.
- Make microphone, recording, and live-audio access separately visible.
- Require explicit approval for new or elevated capabilities.

The receiving GUI remains authoritative for local UX policy. A custom app may
request live audio or recording, but it cannot override local mute, schedule,
consent, or emergency-stop policy.

## Platform approach

The first implementation can target macOS application bundles and use the
application executable path from the manifest. Later platforms can map the
same manifest and session model to their native application identifiers and
launch mechanisms.

The logical contract should remain platform-independent:

```text
manifest → registered app → scoped session → local Nufon API
```

## MVP

Implement:

1. Explicit app registration.
2. Manifest validation.
3. Chat-window `Open with…` action.
4. One-time session token creation.
5. App launch with `--nufon-session`.
6. CLI commands for session inspection and message send.
7. Capability approval for message operations.
8. Session expiration and revocation.

Defer:

- automatic app discovery;
- arbitrary app-to-app invocation;
- direct private-key access;
- media capabilities;
- cross-platform registration;
- dynamic plugin loading inside the Nufon process.

## Open questions

- Should registered apps be identified by package signature, path, or both?
- Should Nufon launch one app instance per conversation or reuse an instance?
- Should a custom app receive events only after launch, or can it subscribe before launch?
- Should the built-in chat remain the fallback for every interaction type?
- Which session transport should replace subprocess CLI calls when persistent
  event subscriptions become important?

## Decision

Use explicit app registration and a manifest to determine which custom apps
Nufon can launch. Pass an opaque, scoped session token at launch. The custom
app uses that token with the standalone Nufon CLI or local service to obtain
approved identity, peer, conversation, and capability context.
